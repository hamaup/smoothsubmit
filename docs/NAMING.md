# SmoothSubmitの命名記録

調査・更新日：2026年10月7日\
状態：2026年10月7日にSmoothSubmitを正式採用。以下の比較は決定前の記録。利用者テスト・商標調査・公開名の確保は未実施

## 採用結果

正式名は**SmoothSubmit（スムーズサブミット）**。利用者の採用指示に基づき決定した。タグラインは「審査の手戻りを、提出前に減らす。」、短い説明は「App Store提出前の監査・修正アシスタント」。CLIはsmoothsubmit、npm配布名は@smoothsubmit/cliを予定する。公開識別子の確保は公開準備時に行う。

## 決定前の検討結果

命名の中心を、利用者が得る「審査による手戻りを減らし、提出の準備を整える」へ置く。AIや検査方式は説明文で伝える。

比較候補はSmoothSubmit、RetryLess、SetToShip。現段階の机上評価では、提出という用途とスムーズに進む成果を結び付けるSmoothSubmitを先頭に置く。ただし、追加調査で近似名のHTMLフォーム用OSS「smooth-submit」が見つかった。名前を完全に独自とは扱わない。対象開発者に意味・発音・記憶を確認する前の仮説であり、正式採用ではない。

ReleaseworthyとReviewPatchは推奨から外す。以前の作業名releaseworthyは、正式採用に合わせて仕様書のCLI・Skill・設定・保存先から置き換えた。

## 調べた命名プロセス

### 1. 候補を作る前に、ブランドが約束する価値を定める

[Igorのポジショニング手順](https://www.igorinternational.com/process/brand-positioning-company-product.php)は、命名前に製品の位置付けを明確にする。[Lexicon創業者のインタビュー](https://www.lexiconbranding.com/live-on-tbpn-naming-strategy-chatgpts-bad-habits-rebrand-pitfalls/)でも、戦略ワークショップで目標や伝えるべきことを整理している。

この製品では、対象者が困る提出後の修正・再提出・待ち時間を出発点にする。「iOS向け」「AI監査」という機能を並べるだけで終わらせない。

### 2. 説明する名前と、価値を連想させる名前を区別する

[Igorの名称分類](https://www.igorinternational.com/process/evocative-product-company-names.php)は、機能を説明する名前と、経験やブランドの位置付けを連想させる名前を区別している。理解しやすさと独自性の配分を決める材料とする。

[Impeccableの公式サイト](https://impeccable.style/)では、名前に加えてAIエージェントのデザイン支援という用途が説明されている。私の分析では、参考にすべきなのは「品質を連想させる名前＋具体的な用途説明」という組み合わせ。英語の形容詞や接尾辞を似せること自体を目標にしない。これはサイトの観察に基づく解釈であり、作者の命名意図を確認したものではない。

### 3. 好みだけで決めず、同じ項目で比較する

[Igorの評価基準](https://www.igorinternational.com/process/name-evaluation-brand-evaluate-names.php)には、競合との区別、位置付けとの関係、音や発音のしやすさ、見た目などがある。今回も比較項目をそろえる。机上の評価を顧客調査の結果として扱わず、根拠のない点数は付けない。

### 4. 言語・利用者・既存利用の確認を別々に行う

[Lexiconの命名サービス](https://www.lexiconbranding.com/our-services/)は、候補開発、言語・文化の評価、顧客調査、商標評価を組み合わせている。名称を生成することと、採用できる名称を選ぶことは別の工程と捉える。これらは各社が公開する実務上の方法であり、特定の名前の成功を保証する研究結果ではない。

[USPTOの説明](https://www.uspto.gov/trademarks/basics/strong-trademarks)では、米国において、暗示的な名称や造語等と比べ、単に商品・役務を説明する名称は商標として弱くなりやすい。一般的な機能名へ寄せすぎない理由になる。ただし、この説明から今回の候補の登録可否や日本での権利状況は判断できない。

## 比較に用いる基準

次の順で評価する。調査を踏まえて本製品用に定めた基準であり、命名会社の評価表をそのまま転用したものではない。

1. **価値との関係**：手戻り削減・提出準備・スムーズな提出を連想できるか。
2. **用途の誤読**：共通の副題を添えたとき、口コミ管理やコードレビュー専用と間違われないか。
3. **言いやすさ・書きやすさ**：日本語の紹介、英語の発音、綴り、CLI入力で扱いやすいか。
4. **独自性・記憶**：近いサービスと混同しにくく、少し時間を置いても思い出せるか。
5. **広がり**：検査機能から修正・再確認・提出情報の支援へ拡張できるか。

明白な既存サービスとの衝突は候補除外の条件とする。商標や配布名の取得可否は別途確認する事項であり、未調査のまま評価点を付けない。

## 前回案を推奨から外す理由

| 候補 | 判断 |
| --- | --- |
| Releaseworthy | 利用者から「価値がわかりづらい」と指摘された。公開にふさわしい品質という広い意味で、提出前の手戻り削減につながりにくい。worthyの説明も必要になりやすい |
| Submitworthy | worthyによる分かりにくさが残る。前回案の語を置き換えるだけでは指摘を解消しない |
| ReviewPatch | 審査と修正という機能は表すが、コードレビューの修正と混同しやすい。[MicrosoftのAPI](https://learn.microsoft.com/en-us/javascript/api/azure-devops-extension-api/reviewpatch)にも同じ語がある。成果を中心にする今回の方針では推奨しない |
| ReviewSail | 審査をスムーズに進める比喩だが、Sailの連想を説明する必要があり、Reviewの意味も曖昧。上位候補から外す |

## SmoothSubmitの追加調査

確認日：2026年10月7日。完全一致に加え、Smooth Submit、smooth-submit、App Store・GitHubとの組み合わせも検索した。

### 名称の既存利用

[smooth-submitの公式GitHub](https://github.com/shridharkaushik29/smooth-submit)は、HTMLフォームやリンクでページ遷移を防ぎ、Ajaxで送信するライブラリ。同じ開発者向けOSSの領域に近似名が存在する。App Store審査支援の直接競合ではないが、名前の独自性と検索上の区別には影響する。

[npm公式レジストリ](https://registry.npmjs.org/smooth-submit)で、smooth-submitが公開済みであることも確認。最新バージョンは1.1.1、同バージョンの公開日は2018年11月21日。古い公開物であることを、名称や権利が自由に使える根拠にはしない。

SmoothSubmitという表示名のApp Store審査支援サービスは今回の公開検索では特定できなかった。商標を検索エンジンで探しても結果を得られなかったが、これは商標データベースの照会とは異なる。登録商標・類似商標の正式確認は未実施。

判断：SmoothSubmitは、同名の直接競合が確認されなかったため引き続き候補にできる。ただし、近似名の開発者向けOSSがあるため「競合も既存利用もない」とは説明しない。採用する場合、App Store向けの副題を常に添え、配布には専用スコープ付きnpm名（例：@smoothsubmit/cli、スコープの確保は未実施）を検討する。

事業上の差別化案は、既存のAIコーディング環境で実装を確認し、根拠付きの検査と修正後の再検査を繰り返せるOSSという位置付け。競合にも監査と修正の機能があるため、Audit → Fixだけを独自性として主張しない。これらの比較から得た本製品への提案である。

## 正式決定前に行う短い検証

対象に近い開発者5〜8人程度への定性的な確認を提案する。人数は本検討の実務上の提案であり、統計的な検証に必要な人数という意味ではない。この確認は未実施。

1. 名前だけを短時間見せ、「何に役立つと思うか」を自由回答で確認する。
2. 全候補に同じ説明文を添え、伝わる便益と誤解を確認する。表示順は入れ替える。
3. 口頭で名前を伝え、綴りを再現できるか確認する。日本語・英語の両方を意識する。
4. 少し時間を置き、名前を思い出せるか確認する。
5. 「審査に必ず通る」「再提出がなくなる」「提出を自動実行する」といった誤読が多い候補は見直す。

好みの投票だけで終えず、意図した価値が伝わったかを採用判断に使う。最終候補を絞った後、想定する公開地域・用途の商標と配布に必要な識別子を確認する。そのうえで正式名を決め、仕様書・CLI・Skill・設定・保存先を一度にそろえる。

OSSの初期配布では、リポジトリ・Skill・CLIで識別しやすいことを重視する。完全一致の.comの確保を命名の最初の条件にはしない。これは本製品の配布方針に基づく判断である。
